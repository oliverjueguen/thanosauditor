## Method

In P3 we did not have the Practice 1 (P1) code, only its report as a PDF. The
requirements were **derived from the functional description in the P1 report** and are numbered here
for the first time; this numbering (RF-xx / RNF-xx) is the canonical one for all of P3. The P3
code is a **reconstruction** of the P1 design (the report states this), validated
with the two real bundles the team generated in P1 (`fixtures/bundles/`).

### Statuses (assignment brief vocabulary, section 3)

| Status | Meaning |
|---|---|
| **Done** | Implemented and tested in P3 |
| **Partial** | Partly implemented, or could not be verified in its real environment; what is missing is explained |
| **Pending** | Defined but not implemented in P3; justified |
| **Modified** | Requirement reworded ("to be reviewed"): original version, new version and reason are given |
| **Dropped** | Not implemented; justified |

**Origin** column: *P1* = described in the P1 report; *P1-roadmap* = from the P1 improvement
roadmap; *P3* = added because the P3 assignment brief requires it.

## Modified, downgraded or pending requirements (original → new → reason)

**M-1 · RF-01 Catalog.**
*Original:* a scraper that dumped the Microsoft catalog (MSUs, updates and CVEs) into a Neo4j
graph on a Raspberry Pi, with millions of nodes.
*New:* RDF/OWL ontology in Turtle (`thanos/ontology/thanos-schema.ttl` + `data/ontology/catalog.ttl`)
queried with SPARQL, populated with the bundles and with the **official MSRC CVEs** (CVRF API,
2026-Apr document: 115 Windows Server 2022 CVEs, 114 fixed by KB5082142). KBs are
resolved live against the catalog (RF-02). The catalog is the **source of the candidate CVEs**
used by the auditor and the panel (SPARQL query); the MSRC extract is only the fallback if the
catalog does not exist or does not know a binary.
*Reason:* Neo4j does not fit in a repository and cannot be installed from scratch without infrastructure
(breaks RNF-04). The CVRF API is the official, structured source of CVEs, more reliable than
scraping HTML. Trade-off: the "millions of nodes" volume of P1 is not reproduced, only
the subset that the cycle triage uses.

**M-4 · RF-04 Baseline from the ISO/WIM (Pending).**
Requires a Windows Server 2022 machine with permissions to mount ISO/WIM and ~10 GB; it was not
reimplemented in P3. Its output (the starting DLLs) is only used by RF-05, and the
real P1 bundles cover the downstream result. Manual procedure in
`docs/02_coordinator_executor.md`.

**M-5 · RF-05 Reconstruction scope.**
The `ApplyDeltaB` binding was verified on Windows 11 (build 26100) with **PA30** deltas
generated with `msdelta` from real binaries: identical SHA-256 with and without the CRC32
prefix and no memory leaks (`docs/evidence/rf05_msdelta_windows.log`). The deltas in the
Windows 11 24H2 store are **PA31** (`UpdateCompression.dll`) and are out of scope:
Windows Server 2022 uses PA30. Reconstruction with the real WS2022 MSUs was done in P1
(its bundles prove it) and was not repeated in P3.

**M-10 · RF-10 bootstrap without MCP.**
*Original:* `bootstrap.ps1` installed `pyyaml` and the Ghidra headless MCP package.
*New:* it installs `pyyaml` and `rdflib`; Ghidra is invoked directly (M-13).
*Reason:* the MCP was only the bridge for Claude Code to drive Ghidra; without it the runner is
reproducible and testable.

**M-13 · RF-13 Ghidra without Claude Code or MCP.**
*Original:* each team member drove the run with Claude Code and the Ghidra headless MCP,
guided by `CLAUDE.md`.
*New:* `run_diff.py` calls `analyzeHeadless` with the `ExportFacts.java` post-script (included in
the package) and exports the **full list** of functions and exports. `executor/CLAUDE.md` is
kept in case the team member wants Claude Code to guide them.
*Reason:* reproducibility (same result without depending on an agent) and automated tests.
*Verification:* Ghidra 11.0.3 + JDK 17 on `upnphost.dll` (1429 functions, 6 exports, 28 s) and
on 3 real Windows Update pairs from the local machine (`msasn1`, `cryptbase`, `nsi`, 8875→9444):
`docs/evidence/rf13_executor_ghidra_real.bundle.json`.

**M-16 · RF-16 Auditor with Claude.**
*Original:* local LLM with `llama.cpp` and a prompt pack.
*New:* Claude via the **Claude Agent SDK**, with the user's own Claude session
(subscription; login with `python -m thanos.auditor.cli login`). The model runs **without
tools** (`tools=[]`, `permission_mode="dontAsk"`, no MCP or settings), one query per
cycle, with names extracted from binaries marked as untrusted data and with strict
validation of the answer. If Claude is not available, the heuristic report is the fallback.
*Reason:* installing and serving a local model is heavy and not reproducible for a third party; the
team asked to use its subscription. Each user uses their own credentials: the product does not
offer claude.ai login to third parties (Agent SDK note).

**M-20 · RF-20 Score formula.**
*Original (P1):* SCORE = |FN+| + |FN−| (functions added + removed by name, Ghidra
noise included; e.g. configmanager2.dll +132/−132 → 264).
*New:* weights per change type (export ×10, import ×3, named function ×2, change in the
function count ×1, string ×1) after discarding Ghidra's autogenerated names. The panel
keeps the P1 figure (`p1_score`) in the tooltip for comparison.
*Reason:* with the real data, the P1 formula would put `clipboardserver.dll` (p1_score 201, almost
all `Unwind@…` noise) above `upnphost.dll` (p1_score 25), while the latter adds 24
network dependencies and matches 8 "Windows UPnP Device Host" CVEs from the same month.

**RNF-01 and RNF-07 (Partial):** see the table; they are explained in the limitations section of the report.

## Improvements over P1 found with the real data

| # | Problem observed in the real bundles | Change in P3 | Requirement |
|---|---|---|---|
| 1 | 80% of the names in the diff (260 of 324) were Ghidra autogenerated names (`Unwind@…`, `Catch@…`, `FUN_…`, `thunk_…`) that "change" only because addresses shift | Filter `thanos/core/noise.py` (first item of the P1 roadmap) | RF-14, RF-20 |
| 2 | `target_build` arrives as a number (`20348.502`): `config.yaml` did not quote it and YAML lost the trailing zero | Quoted template, validation in `run_diff.py` and canonical build derived from `version_after` (`20348.5020`, confirmed by MSRC) | RF-11, RNF-06 |
| 3 | 170 + 14 `C:\Users\<user>\…` paths in the bundles | `python -m thanos.core.sanitize` before publishing | RNF-05 |
| 4 | The same DLL can appear for two executors in one cycle | Binary identity = cycle + person + architecture + name | RF-01 |
| 5 | Delay-load imports (`DelayLoad_*`) counted as functions; CRT helpers as new logic | Scored as dependencies; the report flags toolchain/CRT changes (`fvecerts.dll`) | RF-16, RF-17 |
| 6 | `playready.dll` duplicated in the P1 panel | It was the **wow64** package; the architecture is shown | RF-20 |
| 7 | In 70 of 85 binaries the P1 name list was cut (e.g. 512 of 14,749 functions) | `name_diff_truncated` flag: maximum confidence "medium" from names; the P3 executor exports the full list | RF-14, RF-17 |
| 8 | `diff_manifests` collapsed several DLLs from the same SXS package (2 of 7 with real data) | Key (package without version or hash, DLL) | RF-06 |

**About the data volume:** the P1 "FULL" run is the complete analysis of **one
team member** (85 pairs); the split run assigned 7 binaries per person. Of the latter,
only one team member's bundle is kept (see `fixtures/README.md`).

**Cross-check with real data:** the split (17:52) and FULL (21:57) runs of
2026-05-07 were independent; the two binaries they share (`diagnostic.dll`,
`wdsclient.dll`) have identical **SHA-256 and counts** in both: reconstruction and
analysis are reproducible (`tests/test_core.py::test_reconstruction_is_deterministic_across_runs`).
